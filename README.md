## 시스템 구성

```
질의 → ⑥가드 → ③질의이해 → ④찾기 → ⑤답 → 응답
                              ↑
                    ①자르기 → ②색인 (사전 구축)
```

| 단계 | 구현 | 파일 |
|---|---|---|
| ① 자르기 | 표행·페이지·절차단계 보존, 겹침 300자 | `src/chunker.py` |
| ② 색인 | BM25(한국어 토크나이저 자체 구현) + 임베딩 1024차원 | `src/index_search.py`, `src/build_embeddings.py` |
| ③ 질의이해 | 유형 분류, 역질문 판정, 어휘 확장 | `src/understand_guard.py`, `src/expand.py` |
| ④ 찾기 | **RRF 하이브리드 (BM25 : 임베딩 = 1 : 3)** | `src/hybrid.py` |
| ⑤ 답 | HCX-007 생성 + 근거 표시 | `src/answer.py` |
| ⑥ 가드 | 프롬프트 공격 차단, 단정추천 억제 | `src/understand_guard.py` |

`src/server.py` 가 이들을 묶어 API로 노출한다.

## 성능

자체 평가셋 **100문항 · 채점 체크리스트 606항목** 기준. 설계는 [평가설계.md](평가설계.md),
평가셋은 [eval/](eval/) 참조.

| 지표 | 단일 생성 | **최종** |
|---|---|---|
| 체크리스트 충족률 | 73.0 | **82.2** |
| 함정 대응률 | 92.3 | **98.1** |
| 할루시네이션 | 0.0 | **0.0** |
| 응답 시간(순차) | 18.6초 | 28.4초 |

**같은 설정을 2회 실행한 평균**이다. 실행별로는 체크리스트 83.8 / 80.5,
함정 97.4 / 98.7 이었다. 한 번만 재고 판단하지 않는 이유는 아래 「측정 방법」에 있다.

함정 77문항: 잘못된전제 34 · 대상혼동 18 · 단정추천유도 11 · 정보부족(역질문필요) 11 · 프롬프트공격 3.

### 측정 방법 — 왜 이렇게까지 하는가

**LLM 채점기는 같은 답변에 같은 점수를 주지 않는다.** 저장된 답변을 글자 하나 바꾸지 않고
3회 재채점했더니 73.17 / 73.17 / 74.50% 로 갈렸고(폭 3.33pp), 99문항 중 **29문항에서
항목 판정이 뒤집혔다.** 원본 실행의 76.50% 는 운 좋은 한 번이었다.

**생성도 결정론적이지 않다.** HyperCLOVA X 는 `temperature=0.0, seed` 고정에도
같은 답을 주지 않는다(3회 중 1회가 달랐다 — seed 미지원). 같은 설정을 두 번 돌린
차이가 −1.54pp 였다.

노이즈가 3pp대인데 후보 기법의 효과가 2pp대면 단발 측정으로는 아무것도 판정할 수 없다.
그래서 측정을 다음과 같이 고쳤다.

1. **채점 3회 후 항목별 다수결** — 항목마다 2/3 이상일 때만 충족 (`JUDGE_PASSES`)
2. **같은 설정을 2회 실행**해 평균을 쓴다
3. **문항별 짝지어 비교**로 판정한다. 전체 평균 비교보다 검정력이 높다
4. **대조군을 함께 잰다** — 같은 설정끼리의 차이보다 크지 않으면 채택하지 않는다

이 기준을 적용하니 결과가 크게 바뀌었다.

| 기법 | 짝지어 차이 | t | 판정 |
|---|---|---|---|
| 자기일관성 3회 병합 | **+8.37pp** | **+3.79** | 채택 |
| 페이로드 절감 (topk 20→8, 4096→2048) | +1.75pp | +0.83 | 채택 — 품질은 동급, **25배 빠름** |
| 형제 조각 확장 | −0.39pp | −0.17 | 기각 |
| 프롬프트 변형 6종 | −0.4 ~ +2.2pp | −0.2 ~ +1.0 | 구별 불가 |
| *(대조군) 같은 설정 재실행* | *−1.5 ~ −4.1pp* | *−0.5 ~ −1.5* | — |

페이로드 절감은 **품질이 오른 것이 아니다.** 1회 측정에서는 +4.46pp(t=1.78)로 보였으나
2회로 늘리니 +1.75pp(t=0.83)로 줄었다 — 대조군 변동 이내다. 채택 근거는
**품질 손실 없이 호출당 23~43초를 13~16초로 낮춰** 배포 여유를 확보한다는 점이다.

프롬프트 문구 변형(`prior` / `prior2` / `prior3` / `note` / `both` / `universal`)은
**서로 통계적으로 구별되지 않았다.** 같은 설정을 두 번 돌린 차이가 변형 간 차이보다 컸다.

### 무엇이 효과가 있었나

실패의 성격이 "틀림"이 아니라 **"불완전"** 이었다. 8회 실행에서 한 번도 50% 를 못 넘긴
11문항을 뜯어보니 3개만 검색 실패였고, **8개는 정답 근거가 top-20 안에(때로는 1위로)
들어오는데도** 점수를 잃었다. 답변이 틀린 게 아니라 채점 항목 일부만 담았다.

그리고 실행마다 **다른 항목**을 담았다. 예: Q-096 은 9회 실행에서 `[7,1,3,1,1,1,4,0,0]`.
문항별 최고점만 모으면 73.35% → **92.43%** 였다. 같은 프롬프트 2회만 합쳐도 82.33% 다.

그래서 **초안 3개를 병렬 생성해 하나로 합친다**(`AGENT_SAMPLES=3`).

병합기는 **덧붙이기 전용**이다. 처음엔 "초안들을 합쳐 최종 답변을 쓰라"고 시켰다가
두 번 깨졌다 — 초안이 ~700자인데 결과가 580자로 **요약**됐고, 단정추천 유도 문항에서는
결과가 "사라" 한 마디였다. 다시 쓰기는 압축과 가드레일 재협상을 부른다.
기준 초안을 보존하고 빠진 것만 더하게 하니 두 문제가 함께 사라졌다.

유형별 개선: 종합 +17.1 · 제도 +12.1 · 상품비교 +10.2 · 상품설명 +5.2 · 세제 +4.2pp.

### 근거를 더 주면 더 잘할 것이라는 전제

`topk=20` 은 검색 지표(R@k)가 가장 높다는 이유로 정한 값이었다. 그런데 R@k 는
"정답 조각이 상위 k 에 들어오는가"만 보고 **생성이 그것을 쓸 수 있는가는 보지 않는다.**

컨텍스트를 30,783자에서 13,608자로 줄여도 품질이 떨어지지 않았고(t=0.83),
호출은 23~43초에서 13~16초로 빨라졌다. 이 프로젝트에서 "검색 지표 개선이
답변 개선이 아니다"를 네 번 겪고도, 정작 topk 자체는 검색 지표로 정해둔 채였다.

### 알려진 실패

- Q-082 · Q-053 처럼 근거가 검색되고 초안을 여러 번 뽑아도 못 채우는 문항이 있다.
  채점 항목이 한 문서의 여러 페이지에 흩어져 있고, 모델이 고객 질문에 직접 답하는 쪽을

  신 연금저축계좌 근거가 상위를 차지한다.

## 캐시

`.cache/` 에 색인(40MB)과 임베딩(27MB)이 들어 있고 Docker 이미지에 포함된다.
없으면 기동 시 재생성되는데 **임베딩에만 약 2시간**이 걸리고 API 한도를 소진한다.

`/health` 의 `embeddings` 가 `null` 이면 캐시가 안 실린 것이다. BM25 단독으로도
동작하지만 R@10 이 87.5 → 75.0 으로 떨어진다.

재생성이 필요하면:

```bash
python src/build_embeddings.py
```
