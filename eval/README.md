# 평가셋 (eval/)

단계별 채점용 평가셋. **100문항**(처음 42문항으로 시작해 58문항을 더했다). 채점 방법은 [`../평가설계.md`](../평가설계.md) 참조.

| 파일 | 내용 |
|---|---|
| `evalset.json` | 원본 (프로그램에서 읽을 것) |
| `evalset.csv` | 사람이 보는 용도 |
| `_audit.json` | 근거 대조 감사 결과 |

**함정 문항이 77개(77%)다.** (처음 42문항일 때는 30개, 71%였다.) 과제 평가지표 7개 중 4개가 "잘 답하기"가 아니라
"틀린 걸 바로잡기 / 모르면 되묻기 / 단정 안 하기"를 재기 때문이다.
통짜 파이프라인으로는 구조적으로 못 잡는 부분이라 의도적으로 비중을 높였다.

## 필드

| 필드 | 설명 |
|---|---|
| `id` | Q-001 ~ Q-100 |
| `question` | 고객 구어체 질의 |
| `evidence_file` / `evidence_page` | 정답 근거 위치 |
| `evidence_span` | **파일에서 글자 그대로 복사한 원문** (평균 68자) |
| `extra_evidence` | 추가 근거 "파일:페이지" |
| `answer_checklist` | 채점 항목 (구체적 수치·조건으로 기술) |
| `trap` / `trap_note` | 함정 유형과 바로잡아야 할 내용 |
| `page_note` | 페이지 표기 관련 비고 |

`evidence_span`이 이 평가셋의 핵심이다. **정답이 문서 어디에 적혀 있는지**를 알아야
자르기·색인·찾기 단계를 따로 채점할 수 있다.

### evidence_page = 0 인 경우

두 가지다.

1. **DOCX/XLSX 파생 파일** (`page_note`에 명시) — 원본에 페이지 구분이 없다.
   doc23, doc26, doc35, doc36, doc38~41, doc52 등. 파일 단위로만 근거를 지정한다.
2. **프롬프트공격 문항 2건** — 근거 문서가 없는 게 정답(거절·한계고지).

## 검증 (처음 42문항 기준)

아래 감사는 처음 42문항에 대해 한 것이다. 이후 추가한 58문항은 같은 문자열 대조를 하지 않았다.

생성 에이전트와 별개로 검증 에이전트가 근거를 대조했고, 그 결과를 다시
**기계적으로 재감사**했다 (`evidence_span`이 실제 파일에 글자 그대로 있는지 문자열 대조).

| 항목 | 결과 |
|---|---|
| 근거 스팬이 실제 파일에 존재 | **40 / 40** (공격 문항 2건 제외) |
| 지어낸 근거 | **0건** |
| 페이지 번호 정정 | 1건 (Q-018: KR5119501001 p11 → p7) |
| 페이지 표기 정리 | 10건 (DOCX 파생 → 페이지 없음으로 변경) |

LLM 검증자는 42문항 전부 PASS를 줬지만 그대로 믿지 않고 문자열 대조로 재확인했다.
그 결과 페이지 오류 1건과 표기 부정확 10건을 추가로 잡았다.

## 사용 시 주의

- **이 평가셋은 우리가 만든 것이지 주최측 정답이 아니다.** 실제 평가 데이터셋과 세부 기준은 비공개다.
  과제 안내문의 참고 질의 6개를 씨앗으로 삼되, 문서 근거가 확인되는 범위에서 확장했다.
- 질의는 문서 문장을 베끼지 않고 구어체로 새로 썼다. 그대로 베끼면 검색이 쉬워져 평가가 무의미해진다.
- 100문항에서 짝지어 비교한 표준오차는 약 2.0pp 이고, LLM 채점기 자체가 같은 답변을 3.3pp 범위로
  흔든다. 그보다 작은 차이는 노이즈로 본다(채점 3회 다수결 · 같은 설정 2회 실행 평균).
- `answer_checklist`는 **항목 단위로 채점**한다. 통과/실패 이분법이 아니라 "6개 중 4개 충족" 식으로 센다.
